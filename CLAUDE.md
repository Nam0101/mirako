# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`mirako` is a single-binary Rust CLI (one crate, no workspace) that runs a build on a remote host over ssh: content-hash sync the project up, run the command there, pull the outputs back. The same binary is the client (`mirako run …`) and the remote agent (`mirako serve`). README.md is the user-facing doc and is accurate; keep it in sync when CLI flags, config keys or the Gradle shim change.

## Commands

```
cargo build --release          # binary at target/release/mirako (lto, strip)
cargo test                     # unit tests (every module) + tests/e2e.rs (loopback, see below)
cargo test --lib delta::       # one module's unit tests
cargo test --test e2e          # end to end through the built binary, ~seconds, no ssh
cargo bench                    # criterion: benches/{delta,proto,index,patterns,rewrite,gc,e2e}.rs
cargo bench --bench delta -- --quick
cargo clippy --all-targets
cargo fmt                      # rustfmt.toml: max_width = 140
```

CI is `.github/workflows/ci.yml`. macOS runs on a self-hosted GitHub Actions runner on the m4 (`~/actions-runner`, LaunchAgent service, labels `self-hosted, macOS, ARM64, m4`): fmt + `clippy -D warnings` + `cargo test` on every PR and push to `main` (job `check`), `cargo bench` on pushes to `main` (artifact). The runner's user needs rustup in `~/.cargo`. Linux (x86_64 and arm64, the static musl targets) and Windows (x86_64 MSVC) run clippy + `cargo test` on GitHub-hosted runners (job `portable`). On a `v*` tag matching `Cargo.toml`, `build` makes the four release binaries (`mirako-<tag>-{macos-arm64,linux-x86_64,linux-arm64,windows-x86_64.exe}`) and `release` publishes them with `gh release create`.

`src/lib.rs` exists only so `tests/` and `benches/` can reach the modules; `main.rs` is the CLI on top of it. Unit tests live in each module (`#[cfg(test)]`). `tests/e2e.rs` runs the real protocol without ssh: the project's `mirako.toml` sets `ssh = ["sh", "-c", "exec <bin> serve"]` so client and agent talk over pipes, with `HOME` and `GRADLE_USER_HOME` pointed at a scratch dir so index caches, the global config and the Gradle init script never touch the real home; it is `#![cfg(unix)]` (no `sh`, and no `HOME` sandbox, on Windows), as are the unit tests about symlinks and permission bits; the benches compile on Windows but run on Unix only, for the same reason. Tests that open an `Index` or call `gc::collect` outside that sandbox must delete the cache file they create (`Index::cache_path`) and set `GRADLE_USER_HOME`. Behaviour against a real host is still checked manually (`mirako check`, then `mirako ./gradlew assembleDebug` in an Android project). `mirako gradle-shim print` shows the generated init script without installing it.

## Architecture

Flow of one `mirako run`: `main.rs` (clap) → `config.rs` (global toml overlaid by project `mirako.toml`, `--host` wins) → `client::run` which opens one `Session` (an `ssh host 'mirako serve'` child, stdio piped) and does push → exec → pull on that single connection, then prints stats.

- `proto.rs` — the wire protocol: `u32` big-endian length + postcard frame, `Req` (client→agent) / `Resp` (agent→client). Transfers are pipelined: `Put`/`Delta`/`Delete`/`Symlink` are sent without waiting; only `Flush` (answered by `Ack { failed }`) and `Manifest`/`Sigs`/`Exec`/`Pull`/`Fetch`/`Gc` are request/response. Requests are queued ahead of the replies they do not depend on: the push's `Manifest` goes out in the same write as `Hello` (an agent that sees a foreign version answers the `Hello` and exits so it never acts on what follows), `Exec` right behind the push's `Flush`, and `Pull` — the client's manifest of the download scope plus the signatures of its big files, built on a thread while the command runs — followed by `Gc` when `gc_after_pull` is empty; the agent answers `Pull` by scanning, diffing against `have` and streaming `Put`/`Delta`/`Symlink` up to `End`. `Fetch` only resends whole the deltas that rebuilt to the wrong hash. After an `Ack` with failures the agent refuses `Exec` until a clean `Flush`, and the client drops that reply, resends the files whole and queues again. `VERSION` is the crate version and both sides must match exactly, so bumping `Cargo.toml` is a protocol break; `Session::connect` absorbs it by installing this binary as the agent (`remote_install`) and retrying once, as it does when the remote shell exits 127 (no agent at `remote_bin`) or 0 without answering (`serve` ends cleanly on a frame it cannot decode: an agent up to 0.4, whose frames were bincode).
- `client.rs` — `Session::{connect, push, pull, gc}` plus the free `exec_output` (reader only) and `pull_request`; `run` drives the phases: while `exec_output` prints the command on the main thread, a scoped thread owns the writer, scans the local pull scope, computes signatures (rayon) and sends `Pull` (+ `Gc`), so `pull` only receives. Push mirrors local → remote (sends deletes); pull never deletes locally. Delta senders on both sides use the hash from the scan (`Entry::hash`), never re-hash the file. `run` and `check` start with `shim::refresh` (see shim.rs). `run` then holds `lock_project` to its end (a `File::lock` on `<hash>.lock` next to the index cache; none when the cache dir cannot be written, and let go before a local fallback): a second run of the project waits, so no run scans a tree another one is writing into. `push` sends a `local.properties` as `portable_properties` leaves it (no `sdk.dir`/`ndk.dir`/`cmake.dir`) and patches its scan entry to that content, so the host's copy diffs as in sync; `Config::download_excludes` always lists the file, so it never comes back. The `Exec` carries `forwarded_env`, the variables the `env` config key names. `ssh(cfg)` builds the ssh command every remote call uses; `remote_install` copies this binary when `uname -sm` matches on both sides and otherwise runs `cargo install --git … --tag v<VERSION>` on the host (so release tags matter; exit 3 of that script means no cargo there). Fallback: if ssh fails and `fallback = true`, `run_local` runs the command locally with `MIRAKO_LOCAL=1`.
- `server.rs` — `serve()` loop. Stateful: `Manifest` (or `Pull`, both via `open_root`) must precede `Put`/`Delta`/`Delete` (it sets the root and opens the index). Exec sets `MIRAKO_REMOTE=1` on top of the client's `env`, runs the command in a process group of its own and pumps stdout/stderr as `Resp::Output` frames from two threads sharing a mutexed writer. Requests are read by a thread into a small `sync_channel` (`READ_AHEAD`), because the loop is busy while a command runs: stdin reaching EOF then (the client was cancelled or killed) makes `Hangup::stop` send SIGTERM to that group, and SIGKILL after `GRACE`. The group stays registered until the output pumps end, not just until the command is reaped: a child it left behind holds their pipes open and has to stop too. Once `Hangup::gone` is set the loop serves nothing more, so the `Pull`/`Gc` read ahead never scan a tree the client's next run may be pushing into. Logs go to stderr only; stdout is the protocol channel, so never `println!` in server code.
- `index.rs` — blake3 manifest with a persistent cache keyed by (size, mtime); cache file lives under the OS cache dir (`~/Library/Caches/mirako/<hash>.idx`), one per project root path. Hashing is parallel via rayon, and files ≥ 1 MB go through blake3's mmap + rayon path. `Sigs` is the client's cache of block signatures for the big files of the download scope (`<hash>.sig` next to the `.idx`, same (size, mtime) key), so building a `Pull` only reads the big files that changed since the last run (a pulled APK is read once more on the next run, which happens while that run's command executes).
- `delta.rs` — rsync algorithm (64 KB blocks, weak rolling checksum + truncated blake3). Used in both directions for files in `delta_worthwhile` range (256 KB–1 GB) that exist on both sides. A delta that rebuilds to the wrong hash is reported back and the file is resent whole.
- `xfer.rs` — receiving side shared by client and agent (`Inbox`): writes to `.mirako.<name>.tmp` next to the destination and renames on completion. `safe_join` rejects `..` and absolute paths (on Windows also `\` and `:`); every relative path from the wire must go through it. `canonical` is `canonicalize` without the `\\?\` prefix Windows adds, under which `/` is no separator: every root is made with it, never with `canonicalize`.
- `gc.rs` — housekeeping the agent runs on `Req::Gc` (after every run that pulls, after one that does not when `gc_days > 0`, and on `mirako gc`): removes the project copies under `remote_folder` not synced for `keep_days`, identified by the agent's index cache file for that root (`Index::cache_path`), whose mtime is the last sync because `Index::save` touches it even when nothing changed; deletes `build` patterns inside the current copy (after the pull, with the `!include` semantics of the sync); writes/removes `~/.gradle/init.d/mirako-gc.gradle` for Gradle's own cache retention. A gc error is a warning on the client, never a failed build. `Index::scan` deletes `.mirako.*.tmp` leftovers on both sides.
- `patterns.rs` — rsync-like excludes compiled to globset (`build` = any depth, `/x` = anchored, `*` never crosses `/`, `!x` keeps a path inside an excluded dir; the walk only descends into ancestors of an include). `exclude_local` (not uploaded) / `exclude_remote` (not downloaded) / `exclude_common` (neither); the `*_extra` config keys append.
- `rewrite.rs` — replaces the remote project path with the local one in streamed build output, line-buffered.
- `progress.rs` — `Progress`, the line a transfer of more than a second writes to stderr: redrawn in place on a terminal (padded with spaces, no escape codes), a line every 5 s otherwise, nothing with `--quiet` (`Session::quiet`). `Session::push` counts file bytes against the total it is about to send (a delta frame is an estimate, exact at the end of the file); `Session::receive` counts the bytes off the wire.
- `shim.rs` — the Gradle init script as a string constant (`INIT_SCRIPT` with the `__BIN__` and `__CHECK__` placeholders; `__CHECK__` becomes the `mirako check` handshake block, or a comment when the global config has `shim_check = false`, a key `Config::load` rejects in a project file). It redirects Gradle to an empty stub project under `~/.gradle/mirako/stubs/` and registers one `mirako` Exec task; it bails out (local build) on `updateDaemonJvm`/`wrapper` tasks, tasks that need a device attached to this machine (`uninstall…`, `connected…`, `deviceCheck`, and every `install…` but the next ones), `MIRAKO_REMOTE`, `MIRAKO_LOCAL`, `-x mirako`, `-Pmirako.disabled`, `mirako.enabled=false` in `local.properties`, or a failed `mirako check`. An `install<Variant>` task of a debug or release variant goes to the host as `assemble<Variant>`, and the `mirako` task's `doLast` (`adbInstall`) then runs `adb install -r -t` on every attached device with the APK that `build/outputs/apk/**/output-metadata.json` names for the variant; several APKs (splits) is an error pointing at `-x mirako`. `install` writes it for this binary (`mirako gradle-shim install`, `mirako setup`); `refresh`, called first thing by `client::run`/`check`, rewrites an installed script only when it names this binary and differs, so a dev build never hijacks the installed one. Edits here are Groovy inside a Rust raw string; test with `mirako gradle-shim print`.
- `setup.rs` — `mirako setup [--host]`, each step idempotent: the global config (`config::sample_global`), `ensure_ssh_access` (batch `ssh host true`; on `Permission denied`/`Host key verification failed` with a real `ssh`, `ssh-keygen` when no identity exists and then an interactive `ssh-copy-id`), `report_host` (one probe script in the host's non-interactive shell; `describe` turns its `key=value` lines into a summary line plus warnings for no java, no `ANDROID_HOME`, less than 10 GiB free), `shim::install`, `client::check` (which installs or updates the agent).

Paths on the wire are always `/`-separated and relative to the project root; `~/` in `remote_folder`/`remote_bin` is expanded by the remote agent (`server::expand_home`), not the client.

Unix (macOS, Linux) is the whole product; Windows is a client only (`serve` compiles there but a Windows build host is not supported). The platform seams are few and `cfg`-gated in place: `index::mode` (no permission bits on Windows: everything is 0755 so a pushed `gradlew` runs on the host), `xfer::{canonical, set_mode, make_symlink}` (Windows makes no symlinks: `Session::receive` counts the ones the host sent and warns), the 100 ns mtime rounding in `Inbox::finish` (NTFS), `gc::free_space`, `server::signal_group` and the process group of `server::exec` (a cancel stops nothing on a Windows host), `client::local_program` (`./gradlew` falls back to `gradlew.bat`), `shim::this_binary` (`/` in the path written into the Groovy string), and `LineRewriter`, which writes a Windows root as `/C:/…` behind `file://`. `libc` is a `cfg(unix)` dependency. Nothing on a Mac runs the Windows code: the `portable` CI job is where it is linted and its unit tests run. A local `cargo clippy --target x86_64-pc-windows-msvc` type-checks it, but needs a C toolchain for that target (zstd, blake3, and criterion's `alloca` with `--all-targets`).
